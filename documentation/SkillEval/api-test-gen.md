## Кейс 1 — Read-only эндпоинт из OB

**Вход (точный запрос агенту):**

> Прочитай `documentation/{Service}ObservableBehaviour.md` и сгенерируй тесты для
> эндпоинта `{read-only endpoint}` через /api-test-gen. Service = {Service}.

**Обязано:**
- [ ] Сначала план: Part 1 (таблица сидов) + Part 2 (полный список имён методов, категорий, целевой файл, created/modified) → STOP на согласование; кода до «да» нет
- [ ] Перед кодом — чтение всех Rules/*.md (в отчёте видно, что прочитаны)
- [ ] Тесты ровно по одобренному плану: ни лишних, ни выпавших (сверка план↔код таблицей до format/тестов)
- [ ] У каждого теста `[Category]`, у класса `[Category("{Service}")]`, у методов `[Description]`
- [ ] Только FluentAssertions (`ShouldHaveStatusCode` и др.); типизированные модели; async; без комментариев
- [ ] Эндпоинты/ID из `{Service}Endpoints.cs`; несуществующие ID — динамические (maxId+1), не 999
- [ ] Таблица результатов прогона (метод/категория/результат/ошибка) — запуск зелёный
- [ ] JSON-отчёт проходит `Scripts/validate-skill-report.ps1` → PASS
- [ ] Модели: `ModelResponse`/`ModelRequest`, атрибуты на отдельных строках; константы в Endpoints

**Запрещено:**
- [ ] `Assert.*` (NUnit), `JsonElement`+`TryGetProperty`, синхронный `Execute`, `Thread.Sleep`
- [ ] Хардкод URL/эндпоинтов, статические «несуществующие» ID, выдуманные тексты ошибок
- [ ] Генерация кода до одобрения плана; дублирование существующих файлов
- [ ] Коммит-предложение при красном гейте; красный прогон в отчёте
- [ ] Комментарии, магические числа, однострочные lambda-параметры (`p =>`)

## Кейс 2 — Обязательные поля и 422-негативы

**Вход (точный запрос агенту):**

> Прочитай `documentation/{Service}ObservableBehaviour.md` и сгенерируй тесты для
> write-эндпоинта `{endpoint}` через /api-test-gen, особенно негативные кейсы.
> Service = {Service}.

**Обязано:**
- [ ] План включает минимум 5 активных негативов (`[Ignore]` в счёт не идёт)
- [ ] Отдельный `*_Missing{Field}_*` негатив на КАЖДОЕ обязательное поле тела (пустое тело не заменяет)
- [ ] Негативы с динамическим несуществующим ID (maxId+1) и статическими 0/-1 только как «всегда невалидные»
- [ ] `ShouldHaveError` с текстом из OB (или `[Ignore]` с объяснением для задокументированного бага API)
- [ ] Гарантия данных: GET пусто → POST в OneTimeSetUp → очистка в OneTimeTearDown (последний член)
- [ ] `ShouldMatchRequest()` для POST/PATCH-сравнения request↔response
- [ ] Write-данные вымышленные, варьируются ≥2 размерностей через `DataGenerator`
- [ ] Сверка план↔код + таблица результатов + validator PASS (как в кейсе 1)

**Запрещено:**
- [ ] Негатив-«заглушка» один на весь эндпоинт вместо одного на обязательное поле
- [ ] Статический 999 как несуществующий ID; хардкод endpoint-путей
- [ ] `[Ignore]` без объяснения; выдуманный текст ошибки, отсутствующий в OB
- [ ] Cleanup в `finally`-на-test-методе; пересечение Api+E2E в одном прогоне без Offset
